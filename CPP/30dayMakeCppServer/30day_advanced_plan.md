# 30dayMakeCppServer 后续进阶教程 (Day 17 - Day 30) 规划计划

原作者的开源项目 `30dayMakeCppServer` 实际上并未完成 30 天的全部更新，项目的主线代码更新到 `day16`（使用智能指针重构、完善工程化）便基本停止了。

为了帮你补齐“30天”的学习闭环，结合企业级 C++ 高并发服务器的核心组件（如网络库 Muduo 的经典架构），我为你定制了 **Day 17 到 Day 30 的进阶开发教程概览**。后续我们可以按照这个大纲，每天推进一个模块的开发。

## 阶段一：应用层协议与 HTTP 解析 (Day 17 - Day 20)
目前我们的服务器只是一个底层的 TCP 字节流转发服务器（Echo Server），接下来我们将让它能够听懂 HTTP 协议，成为一个 Web 服务器。

*   **Day 17：完整的 Buffer 类重构与数据边界处理**
    *   **目标**：解决 TCP 粘包和半包问题。
    *   **内容**：重构目前的 `Buffer` 类，引入类似 `std::vector<char>` 的连续内存或链式内存管理，设计基于分隔符（如 `\r\n`）或固定长度的读写接口。
*   **Day 18：有限状态机 (FSM) 引入与 HTTP 请求解析请求行**
    *   **目标**：理解状态机模式，能够解析 `GET /index.html HTTP/1.1`。
    *   **内容**：定义 HTTP 请求类 `HttpRequest`，使用有限状态机逐字符解析 HTTP 请求行和头部。
*   **Day 19：HTTP 头（Headers）和 Body 的解析**
    *   **目标**：完整解析 HTTP 请求的所有部分。
    *   **内容**：解析和存储键值对头部（User-Agent, Content-Length等），处理 GET 和 POST 请求的正文提取。
*   **Day 20：构建 HTTP 响应 (HttpResponse) 并实现静态文件服务**
    *   **目标**：根据请求返回真实的网页内容。
    *   **内容**：实现 `HttpResponse` 类。如果请求了 `index.html`，服务器能从本地磁盘读取该文件并构造出 `200 OK` 响应报文返回给浏览器。

## 阶段二：定时器机制与超时连接剔除 (Day 21 - Day 24)
网络编程中，处理不活跃的连接（空占资源但不发消息）非常重要。我们需要定时器来定期踢掉“占着茅坑不拉屎”的恶意客户端。

*   **Day 21：Linux 定时器 `timerfd_create` 的使用**
    *   **目标**：了解如何在 Linux 下使用文件描述符来管理时间。
    *   **内容**：学习 `timerfd` 的 API，并将其纳入现有的 `Epoll` 事件轮询机制中（因为 Unix 下一切皆文件，时间也是事件）。
*   **Day 22：优先队列 (Min-Heap) 实现定时器管理器**
    *   **目标**：高效地管理海量定时任务。
    *   **内容**：实现一个 `TimerQueue`，基于小根堆结构，使得每次都能 O(1) 取出最近需要超时的那个任务。
*   **Day 23：服务器超时连接剔除机制**
    *   **目标**：自动清理死连接，防护简单的单机 DDoS（如慢速连接攻击）。
    *   **内容**：在 `Connection` 中加入最后活跃时间戳。每次 `Epoll` 唤醒时检查 `TimerQueue`，将超时的 `Connection` 主动踢掉（Close）。
*   **Day 24：HTTP Keep-Alive 的支持**
    *   **目标**：支持长连接，提升浏览器访问性能。
    *   **内容**：解析 HTTP 头部的 `Connection: keep-alive`。如果存在，则在请求完成后重置定时器而不是直接断开；如果不存在，则发完响应即断开。

## 阶段三：日志系统抽象与异步日志 (Day 25 - Day 27)
现在的代码里全都是 `printf` 和 `perror`，这在生产环境中是致命的（IO 阻塞会导致并发性能拉胯）。我们需要一个高性能的日志库。

*   **Day 25：基础日志级别与宏定义封装**
    *   **目标**：规范化日志输出格式。
    *   **内容**：定义 `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`, `FATAL` 级别。使用宏定义获取文件名、行号、当前时间，统一输出格式如 `[2026-03-17 10:00:00] [INFO] [Acceptor.cpp:16] new connection`。
*   **Day 26：双缓冲区机制 (Double Buffering) 设计**
    *   **目标**：理解后端写日志的极致性能优化方案。
    *   **内容**：准备两个 Buffer。前端业务线程只负责把日志写入 Buffer A。写满后，唤醒后台持久化线程去把 Buffer A 刷到磁盘，前端切到 Buffer B 继续写，互相不阻塞。
*   **Day 27：后台异步日志落地线程**
    *   **目标**：完成异步日志组件。
    *   **内容**：利用条件变量 `std::condition_variable` 配合线程，实现日志往磁盘文件（如 `server.log`）的写入。替换掉工程里所有的 `printf`。

## 阶段四：高阶特性与完结 (Day 28 - Day 30)

*   **Day 28：优雅关闭 (Graceful Shutdown) 与信号处理**
    *   **目标**：按 `Ctrl+C` 时不丢失正在处理的数据。
    *   **内容**：捕获 `SIGINT` 和 `SIGTERM` 信号。停止 `Acceptor` 接受新连接，等待线程池中现存的任务和现存的 `Connection` 处理完毕后再关闭进程。
*   **Day 29：接入简单的数据库（MySQL / SQLite 控制连接**
    *   **目标**：具备保存状态的能力，向真实的业务服务器靠拢。
    *   **内容**：引入数据库连接池概念，响应某个特定 HTTP POST 请求，实现简单的用户注册信息的写库保存。
*   **Day 30：项目整体压测、性能调优与回顾总结**
    *   **目标**：检验我们的劳动成果。
    *   **内容**：使用 `Webbench` 或 `Wrk` 压测工具对我们手写的服务器进行压力测试。使用 `perf` 生成火焰图寻找性能瓶颈。总结这 30 天的心得。
