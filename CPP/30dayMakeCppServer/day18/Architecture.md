# Pine C++ Server 整体框架与模块逻辑文档

## 1. 项目整体架构概述
本项目基于 **Reactor 模式** (主从 Reactor 架构) 实现了一个高性能、高并发的 C++ TCP 网络服务器。
整个架构以事件驱动（Event-Driven）为核心，利用 I/O 多路复用（如 `epoll`）来监听套接字事件，非阻塞 I/O 配合应用层缓冲区避免单个连接阻塞整个线程。结合线程池，服务器支持多线程并发处理业务逻辑和网络 I/O，达到了 **One Loop Per Thread**（每个线程一个事件循环）的并发模型。

### 核心运行流程
1. **Main Reactor（主事件循环）** 仅负责监听套接字（Acceptor）并处理新的连接请求。
2. 每一个新建立的连接都会被分配给 **Sub Reactor（子事件循环池，隶属于 ThreadPool）** 中的某一个线程。
3. **Sub Reactor** 负责由于这一分配产生的所有后续网络 I/O 事件（如客户端的数据到达、可写、断开连接）以及具体的数据处理，从而极大降低主线程的负担，提高系统并发接收能力。

## 2. 核心模块逻辑详解

### 2.1 底层底层网络与基础支持模块
* **`Socket`**
  * **作用**：封装底层的原生 `socket` 文件描述符（fd）。
  * **逻辑**：管理 socket 的生命周期（创建、绑定端口 `bind`、监听 `listen`、接受客户端连接 `accept` 等），并提供将 socket 设置为非阻塞模式（Non-blocking）的接口。遵循 RAII 原则，在析构时自动关闭 fd 释放资源。
* **`common.h` / `util.h` / `Exception.h`**
  * **作用**：公用的工具类、宏定义与异常处理机制。
  * **逻辑**：提供全局通用的宏及基础组件（如禁用拷贝构造等）、错误日志输出和捕获机制（基于断言 ASSERT 的严谨性验证）以及网络执行出错时的异常抛出机制。

### 2.2 事件分发机制模块 (核心 Reactor)
* **`Poller` (由于身处 Linux 平台，普遍为 Epoll 封装)**
  * **作用**：封装底层的 I/O 多路复用系统调用。
  * **逻辑**：统一管理要监听的文件描述符及其关注的事件。提供 `UpdateChannel`（添加/修改/删除监听事件）和 `Poll`（阻塞等待直到有事件发生，返回活跃的 Channel 列表）方法。对跨平台开发留有余地，但核心专注 `epoll` 高性能轮询。
* **`Channel` 类**
  * **作用**：连接底层的 `Socket fd` 和高层管理器 `EventLoop` 之间的桥梁纽带。
  * **逻辑**：封装了套接字描述符 `fd` 及其感兴趣的事件（`EPOLLIN`可读, `EPOLLOUT`可写 等），同时它还保存了事件发生时需要触发的回调函数（如 `ReadCallback`, `WriteCallback`）。当 `Poller` 发现 `fd` 有事件发生时，会通知其对应的 `Channel` 调用 `HandleEvent()` 执行特定的回调响应。
* **`EventLoop` (事件循环)**
  * **作用**：核心 Reactor（反应堆），负责真正驱动事件循环并执行 I/O 调度。
  * **逻辑**：每个线程至多只运行这一个 `EventLoop` 对象（One Loop Per Thread）。其包含一个 `Poller` 和一个活跃状态下 `Channel` 的集合。`Loop()` 函数是一个 `while` 死循环，不断调用 `Poller::Poll()` 获取活跃事件，然后分发给相应的 `Channel` 进行处理。

### 2.3 上层组件与服务器功能模块
* **`Buffer` (应用层缓冲区)**
  * **作用**：提供安全、可靠、伸缩性好的数据缓存区，是解决非阻塞 I/O "粘包"、"半包" 顽疾的核心防线。
  * **逻辑**：封装了读和写的缓冲区状态（通常基于 `std::string` 扩展）。当从网络读数据时，先存入 `Buffer` 内部，业务逻辑再从 `Buffer` 取走完整的数据桢；写数据同理，当底层内核的发送缓冲区拥堵时先存入 `Buffer`，待收到系统 EPOLLOUT 回调后再异步处理发送操作。
* **`Connection` (TCP 连接接口)**
  * **作用**：代表和封装一个已经建立通信的 TCP 连接完整生命周期。
  * **逻辑**：内部持有一个 `Socket`，一个关联的事件分发 `Channel`，以及对应的处理输入/输出的 `Buffer`。它接管并负责处理该连接的所有 I/O 操作回调（如 `Read()`、`Write()`），并向更上层业务暴露回调函数的接入接口 （OnMessage, OnConnect 等），进行资源整合与释放掌控。
* **`Acceptor` (连接接收器)**
  * **作用**：专用于处理服务器初始启动后监听 Socket 上带来的新接受事件。
  * **逻辑**：一般驻留在主线程 EventLoop 中，具有独立负责服务器监听套接字的 Channel。当新的客户端请求到达时，`Acceptor::AcceptConnection` 触发，调用内核底层的 `accept` 函数产生一个与客户通信的新 fd，最后通过预设好的回调机制将这 fd 回传给给上层的 `TcpServer` 用作包装连接。
* **`ThreadPool` (线程池机制) / Sub-Reactors**
  * **作用**：实现多线程模型的主从 Reactor 理念——执行从属子事件循环。
  * **逻辑**：在由于并发增高而创建的复数个固定数量工作线程，各个工作线程内部跑着完全属于自己独立的 `EventLoop` 事件泵。新连接经过监听线程后被触发，通过诸如“轮询（Round-Robin）” 的分配策略平均指派给线程池中某一个闲置线程去负责，自此新 client 的一切生死活动只在这个单一子线程里运转，无需进行复杂的加锁保护。
* **`TcpServer` (服务端顶级接口统筹类)**
  * **作用**：向最终用户层（业务开发者）提供的整合顶层接口，负责统筹内部的所有类实现启动与运行。
  * **逻辑**：用户通过它运行代码。对象内部持有一个作为核心的主线程 `EventLoop`、用于接受客户端的 `Acceptor`，以及调度多处理能力的 `ThreadPool`。当 `Acceptor` 接入用户访问时，配合池化处理将对应的 FD 封装成 `Connection` 丢进给定的 Sub-Reactor 里分属管理。对外部抛出方便易用的业务自定义设置，如消息触及钩子函数（`OnMessage`）。

## 3. 典型交互时序说明（生命周期全景）
1. **启动初始化**：用户创建 `EventLoop` 和 `TcpServer`（传入设定的端口），注册一系列事件到达回调（新连接接入后的业务处理、数据通信到达时的业务处理逻辑），调用 `Start()` 启动 `ThreadPool` 和绑定监听服务，接着通过 `EventLoop::Loop()` 启动主死循环。
2. **发生客户端接入请求**：某一客户端发起 TCP 请求，核心线程 `EventLoop` 控制下的 `Poller` 接收到监听端口的可读事件；
3. **分配新连接**：`Poller` 回调对应的 `Acceptor::AcceptConnection`，得到通信使用的全新 FD 后它通知 `TcpServer` ；
4. **子线程接管事务**：`TcpServer` 将原始 fd 创造升华为一个 `Connection` 资源抽象封装。通过轮询机制选用线程池中的一个 Worker(Sub-Reactor) 子线程；该 `Connection` 随即与其生命周期绑定的子 `EventLoop` 的 `Poller` 绑定在一起。
5. **正常的消息通信流动**：由于网络数据的到达，该子线程里的 `Poller` 将检测到的“读就绪”信号通知被关联的 `Connection->Channel` 执行提前写好的读取回调函数；其中会将消息从操作系统的内核抓取至此连接自带的应用态 `Buffer`；在保障数据安全获取完毕后，它最终向外部触及到业务编写人员写下的 `OnMessage(Connection*, string)` 回调。
6. **终止通信与资源回收**：当系统 `read()` 返回了 `0` 标志时（即对端关闭操作触发 EOF），将会触发关闭和清理 `Socket` 销毁动作；通知 Server 从列表清除非活动对象从而触发完全析构回收以防内存泄漏。

## 4. 结语
总概而言，Pine C++ Server 严格基于现代 C++ 特性的解耦思维做出了合理设计，各行其是：  
- `EventLoop` 和 `Poller/Channel` 一同承担了系统繁重复杂的内核事件触发与分发任务；  
- `Socket`、`Connection` 及配合的 `Buffer` 把控了最底层的报文输入与安全保存操作；  
- `Acceptor` 单一处理入口管理，`ThreadPool` 化解了高并发时算力枯竭问题；  
- `TcpServer` 提供给最终架构完美的使用界面。  
多组类构件之间层级关系分明，最终形成了一套不逊色于主流生产环境组件的高效网络并发传输模型！
